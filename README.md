# 🗓️ AniHub —— Anime · Blog · Wiki

全栈多页面网站：**Anime**（当前档期放送时间表，精确到分钟）+ **Blog**（网站更新日志 / 随手记录）+ **Wiki**（笔记，支持 Markdown / 所见即所得 / HTML 文档）+ **Tools**（工具箱）。登录后即可写作，深浅主题按时间自动切换。

数据来源为 [AniList](https://anilist.co) 公开 GraphQL API，无需注册或 API Key。

## 功能

### 视觉与交互

- **导航栏毛玻璃（frosted glass）**：`backdrop-filter` + 半透明面板底色（无渐变，通体均匀）+ 顶部 `inset 1px` 内高光与底部极淡描边；滚动后投影加重形成「浮起」的层次。玻璃参数集中在 `:root` 的 `--nav-bg-alpha` / `--nav-blur` / `--nav-sat`，便于统一微调（**不要在 `.navbar` 里重复定义**，否则会盖掉 `:root` 的值）
  - **页面在顶部时不要「上深下浅」**：此时玻璃身后就是壁纸本身，壁纸顶部偏暗就会透出一条暗色带。实测把 `--nav-bg-alpha` 提到 82%、模糊加到 28px 可把导航栏内部上下亮度差从 **-63 压到 -25**（深色主题 22 → 6.4），同时保持底部与页面背景的融合（差 3.3）。`--nav-sat` 保持接近 1：饱和度提升会放大壁纸色相，浅色主题下容易发蓝
  - **高度必须与断点无关（实测 360→1920px 恒为 49px）**：顶栏高度 = 上下 `padding`（8+8） + **最高的子元素**，所以只要某个子元素在某个断点变高，整条顶栏就长高、里面所有元素跟着上下位移（用户反馈"特定分辨率下 navbar 会变高些，位置也会改变"）。实测子元素高度会在断点处变：**搜索框 28 / 31 / 34px**（`≤900px` 把 input 字号提到 16px 防 iOS 缩放 → 34px）、品牌字 24 / 24.8px → navH **47 / 49 / 51** 三种
    - 解法：引入 `--nav-item-h: 32px`，所有"会参与撑高"的元素都用它定高（`.nav-search`、`.nav-search input`、`.btn-sm`、`.theme-slot`），并给 `.navbar` 一个 `min-height` 兜底
    - ⚠ 搜索框要用 `height` + `box-sizing: border-box` 定高，**不要靠 `padding` 撑**：`padding: 7px` + `font-size: 13px` 算出来 31px，而 `≤900px` 把字号改成 16px 后变成 34px
    - ⚠ 别在 `≤480px` 里改 `.btn-sm` 的 `padding`（那里有 `padding: 5px 8px` 覆盖）—— 高度已被 `--nav-item-h` 钉死，改 padding 不会再影响顶栏高度
  - 高度变化会自动通过 `ResizeObserver` 写进 `--nav-h` / `--wp-shift`（用 `offsetHeight`，整数），阅读页 / 拓扑图 / 控制台等「铺满整屏」的布局都据此贴合，无需各自改常量
  - ⚠⚠ **`position: sticky` 的顶栏曾被"滚动时整条消失"**（用户反馈"甚至会消失"）。根因在 `style.css` 的移动端适配段：
    ```css
    @media (max-width: 768px) { html, body { overflow-x: hidden } }
    ```
    在 body 上设 `overflow-x: hidden` 会让 `overflow-y` 从 `visible` 计算成 `auto`，于是**整个 body 变成滚动容器**；而 sticky 元素是以"最近的可滚动祖先"为基准的 —— 顶栏不再相对视口吸顶，而是相对 body 吸顶，**页面一滚就跟着滚走**。实测 390px 下 `scroll=300 → navbar top=-300`，而 1024px（无该规则）正常为 `0`
    - 修法：改用 **`overflow-x: clip`** —— 它不创建滚动容器，既能抑制横向溢出、又不破坏 sticky（项目里 `.app-shell` / `.graph-full` 早就是 `clip` 写法）
    - 验证：19 个宽度 × 6 个滚动位置 + 多页面（含 `/console` `/game` `/wiki?view=graph`）逐项做**命中测试**（`elementFromPoint` 落在 navbar 内），异常项 0
- **壁纸独立图层**：全站壁纸从 `body::before` 迁到 `src/components/WallpaperLayer.vue`（`.app-shell` 内 `z-index:-1` 的固定图层）。原因是毛玻璃必须能糊到**身后的真实内容**，而 `body::before` 在 `.app-shell` 层叠上下文之下，导航栏透过它只能看到底色、模糊出来是一片纯色。迁移后壁纸仍在所有内容之下，但导航栏能糊到它 —— 这是玻璃感成立的前提
- **Wiki 拓扑（深空场景）顶栏必须与其它页面一致**：导航栏在所有页面、两种主题下都用同一套主题变量（`--panel` / `--text` 等），**不做任何按场景切换配色的特例**。顶栏颜色来自「半透明玻璃 + 身后的壁纸」，所以实测应各页完全相同（浅色主题 `#A0BEDF`、深色 `#1D3554`）。
  - 两个曾经的错误做法（都会让顶栏变成另一块纯色）：
    1. 给导航栏加 `.on-deep-space` 固定深色玻璃 → 浅色主题下顶栏近黑 `rgb(16,22,42)`
    2. **往 `<html>` 刷深空底色**（`html.style.backgroundColor = '#0b1322'`）→ 全站壁纸是 `.app-shell` 内 `position:fixed; z-index:-1` 的图层，会被 `<html>` 的背景整个盖住，而导航栏的 `backdrop-filter` 只糊它正后方的内容 → 顶栏从「壁纸 + 玻璃」退化成「深空纯色 + 玻璃」，浅色主题下变成近白 `#F8F9FC`
  - 深空背景由拓扑区域自己负责：`.graph-full` / `.graph-sky` 是不透明的 `#0b1322`，且该视图高度 = 视口高 − 导航高、不产生文档滚动，因此不需要给 `<html>` 兜底也不会露白边。`colorScheme` 仍保留（只影响原生滚动条/表单控件配色，不参与背景绘制）
  - 回归断言里包含「任何路由都不得往 `<html>` 写内联 background-color」这一条，防止再次踩坑
- **窄屏的品牌抽屉 + 导航栏在所有宽度都是单行**：`≤1024px` 时主导航折进 `AniHub` 旁边的 `.mobile-menu`，悬停 / 聚焦品牌即展开
  - **单行是硬要求**（用户两次反馈"特定分辨率下还是两行"）。实测 **21 个宽度（360 → 1920px）全部 1 行**：`360/390/414/480` navH=47 · `560/640/700/780/820/900` navH=51 · `1000/1024` navH=49 · `1080/1100/1160/1180` navH=49 · `1190/1240/1366/1500/1920` navH=49
  - ⚠⚠ **最大的坑：`≤1180px` 原本就是"两行"设计**。旧写法是「第一行 = 品牌 + 可横滚链接 + 搜索 + 键盘 + 主题；第二行 = 身份/操作」，靠 `.nav-end { flex-basis: 100% }` 强制换行 —— 所以 **1024~1180px 这一段必然是两行**（实测 1100 / 1160 / 1180 都是 navH=88、中心极差 40px）。现在 `≤1180px` 也改成单行：链接 `flex: 1 1 auto; min-width: 0; overflow-x: auto` 自己滚动，搜索 `flex: 1 1 60px` 可压缩，**其余元素一律 `flex: 0 0 auto`** 不参与伸缩，因此再也不会折行
  - ⚠⚠ **`display: contents` 不会清掉容器自己的 `margin` / `padding` / `border`**。`.nav-actions` 带 `margin-left:12px + padding-left:12px + border-left:1px`，在 `≤1180px` 展开成 `display: contents` 后，这些非但没消失，反而变成"搜索与键盘之间凭空多出 **38px** 空档"（实测 390px 下搜索右缘 207、键盘左缘 245）—— 这就是用户说的"**手机下头像/键盘/深色模式的位置不对**"。必须在同一个媒体查询里把它们清零
  - 头像/键盘/主题那一簇现在紧邻且贴右：实测 360~480px 间隙 `[0,0]`、右边距 = 导航栏内边距（10px）；桌面端间隙 `[13,10]`、右边距 20px
    - 桌面那个 13px 是 `.nav-end` 的 `gap: 6px` 叠加 `.nav-actions` 的 `margin-left: 4px`；原先两个值都是 12px（合计 30px），比其它相邻元素明显松，已收小
  - 搜索框只在 `≤560px` 才隐藏。⚠ 阈值取 560 是算出来的：品牌(60) + 搜索下限(60) + 键盘(61) + 主题(77) + 4×10 间距 = 298 < 390−20，所以放得下；早先写在 780px，结果 600~780 之间会留一大段空白（实测 700px 下品牌到 82、右侧那组从 512 才开始，中间空 430px）
  - ⚠ `.nav-end` 的 `order` 必须**显式**写（当前 6）：`.nav-top` / `.nav-actions` 是 `display: contents`，子项直接参与外层排序，`.nav-end` 默认 `order: 0` 会跑到最前面
  - **外观**：抽屉本体是**实底面板**（`--overlay-panel` 不透明 token）+ 细边框 + 14px 圆角 + 阴影；**每个条目各自有底与 9px 圆角**，hover 与当前页分别是 14% / 18% 的 accent 底
  - ⚠ 原版是**完全透明**的一条竖排文字（连条目也没有底），压在壁纸上几乎读不清（用户反馈"展开的条目没有背景"）
  - **展开动画**：像抽屉一样从品牌下方滑出 —— `visibility + opacity + translateY(-8px) → 0`，配 `transform-origin: top left` 与 iOS 弹簧曲线
  - ⚠⚠ 收起**不能用 `display: none`**（那样无法过渡）。改用 `visibility`，并用
    `transition: visibility 0s linear <dur>` 让它在淡出**结束后**才不可见 ——
    否则收起瞬间就点不到了。元素始终留在文档流里，所以「品牌 → 抽屉」的悬停路径也是连续的，
    鼠标经过两者之间那 6px 间隙时不会中途触发 `mouseleave` 把抽屉收掉
  - 桌面宽度下 `display: none` 彻底移除（不留可聚焦的隐藏抽屉）；窄屏由媒体查询改成 `flex`
- **首页背景：真实 88 星座星空（`ConstellationField.vue`）**：星点按**真实星座**的位置落位，同一折线内的相邻星点连线，另加一层很淡的碎星填缝。
  - **数据**：`src/data/constellations88.js` —— 从 d3-celestial 的 `constellations.lines.json` 生成（BSD-3-Clause，见 `scripts/build-constellations.mjs`），含 88 星座 / 150 段连线 / 893 个点。运行时不需要联网，产物随仓库提交；要更新数据跑 `node scripts/build-constellations.mjs`
  - **预处理**做了四件事：① 按 id 归并（Ser 在源数据里被拆成两个 feature）；② **RA 环绕（unwrapping）** —— 星座跨过 RA 0° 时（大熊、室女等）直接取差会得到"横跨整个天区"的假跨度，实测把 Cha 压成 `w=1/h=0.01` 的一条细线，处理方式是把最大的那个空隙找出来、其余点 +360 搬回来；③ 等比归一化到 [0,1] 并居中（真实角尺寸差 10 倍以上，不统一的话小星座看不见）；④ 给极扁的星座（南天的 Oct/Aps/Cha，真实比值只有 0.05）一个 **0.3 的宽高比下限**，轻微非等比拉伸把它撑开，否则放进格子是一根头发
  - **摆放**：每个星座带自己的 `w/h`，按格子尺寸分别缩放，形状不会被压扁拉长。格子约 4.2 万 px²，1400×900 摆 24 个、1920×1080 摆 48 个左右；88 个**不重复地**铺一遍，不够再从头循环并换抖动/缩放/角度
  - **密度踩过的坑**：① 早期把数量上限卡在星座总数（当时只有 6 个），1400×900 只摆得出 3 个；② 只摆 `want` 个时**最后一行常常只占一两格**，那个角落就空着（实测 4×3 分区里出现 0），现在行数定下来后把数量**补满整行**（`n = cols × rows`）；③ 换成 88 星座数据后**密度得收紧** —— 这份数据比原来手写的 6 个稀疏得多（总共 150 段、平均每个星座不到 2 段），格子从 11 万缩到 4.2 万；但也试过 3 万，画面碎成一片、看不出星座形状
  - 连线线宽 1.45、不透明度 0.6（比 6 星座时代粗/亮），因为 88 星座单段太少，太细整片星空看着是散的
  - 星座整体随时间**极慢自转 + 轻微呼吸缩放**（幅度 3.5% / 0.05 rad），形状始终可辨识，但不像贴图那样死板
  - 亮星的光晕用**径向渐变**：先前用"实心圆 + 低透明度"会渲染成有明显硬边的圆盘，亮星看起来像贴了个圆片
  - **去掉了鼠标交互**：早先版本会让靠近光标的粒子被吸引并提亮，视觉上很吵。现在鼠标完全不参与（连监听都不装），只有滚动视差与自身动效
  - 新增 `canvas.dataset.rebuild` 重建标记：切页面回来号不变即证明星空未被重排。**这个标记是必要的** —— 试图用像素比对判断"是否重排"会被闪烁噪声淹没（原地等 9s 的 IoU 只有 32%，导航往返 12.5%，根本分不出来）
- **首页 Logo：三星系统（`HomeLogoMark.vue`）**：三颗星走 **O₂(1.2) 周期轨道** —— 一般三体问题的一条"编舞"周期解，三颗星沿交叉的闭合曲线互相追逐（参考图来自 Li et al. 2023 "New three-dimensional periodic orbits of the general three-body problem"）。
  - **初值**（照参考图，`G = 1`）：
    - 质量 `[1.0, 1.0, 1.2]`
    - 初始位置 `[(-1,0,0), (1,0,0), (0,0,1.02201)]`
    - 初始速度 `[(-0.2726,-0.432094,0.629473), (-0.2726,-0.432094,-0.629473), (0.454333,0.720156,0)]`
    - 周期 `6.90577639826182`
  - **为什么这版用数值积分**（上一版分层构型用的是开普勒解析式）：这是一条**一般三体的周期解**，没有"内层双星 + 外层伴星"那种可分解结构，写不出解析式；只能速度 Verlet 积分
  - ⚠⚠ **这条轨道不能一直积分下去 —— 它是"不稳定"的（混沌）**：
    - 实测（**两个独立步长给出相同的增长率**，所以这**不是积分精度问题**，是轨道本身的性质）：

      | 周期数 | 距初值偏差 (dt=1/50000) | 距初值偏差 (dt=1/200000) |
      |---|---|---|
      | 1 | 3.0e-5 | 3.4e-5 |
      | 4 | 1.17 | 1.17 |
      | 5 | 2.15 | 2.15 |
      | 6 | **204** | **44** |
      | 200 | 117310 | 4353 |

    - 放大率约 **10⁴ / 周期**。也就是说**哪怕把步长缩到 1/200000，几个周期后照样飞出去** —— 靠调步长救不了
    - 现象就是"跑一会儿变轨、最后飞出去"（用户报的就是这个）
    - ⚠ 我第一次验证只跑了**一个周期**（闭合 3.4e-5）就下了"精确周期"的结论 —— 对混沌系统这是**不够的**。长期验证必须跑几十个周期
  - **解法：离线制表 + 按相位查表播放**（不实时积分，也不"到点重启"）
    - 关键认识：解本身在数学上是精确周期的（P 之后精确回到初值），数值积分只是在 P 处留下 3.4e-5 的残差、而这个残差会被混沌放大。所以**只要一直在用"残差还没被放大"的那一段**就没问题
    - 做法：挂载时**把整整一个周期积分成一张高密度表**（`TABLE_HZ = 240` → 约 1658 项），此后画面只是按相位在这张表上走动；相位连续增长、到 1 回绕到 0
    - 为什么不是"每个周期重置回初值"（我先做的是那个）：那样**看得出来"每 7 秒重来一次"**（用户报的就是这个）。查表法没有"起点/终点"的概念，相位是连续绕圈的，所以**没有重启感**
    - 实测：重置法 300 个周期最大半径 **1.0709**（不重置是 **177675**）；查表法天然有界（就是一个周期循环）
    - 性能顺带更好：每帧只做一次线性插值，不再需要每帧跑 ~1600 步积分
  - **接缝为什么看不见**（下面两条都是踩出来的）：
    1. **位置必须跨表尾/表首插值**：只在表内相邻两项插值的话，相位回绕瞬间位置会跳 **~49 用户单位**（实测相邻帧最大位移 51）。改成"从末项插到首项"后降到 **2.5**（这就是轨道在 30Hz 采样下的正常弧长）
    2. ⚠⚠ **尾巴只需要老老实实记录"光点去过哪里"，不要做任何修正**：我曾为了"更顺滑"写过一段"让旧尾巴点按年龄权重追向新位置"的补偿逻辑 —— 结果它把整条尾巴往中心拽，缩成一团乱麻（**这就是用户报的"轨迹线不对"**）。
       - 实测：补偿版尾 0 的最大半径只有 **20.2**，而它真实轨道半径是 **28.5**；去掉补偿后尾巴包围盒 `[3.5,12.3,54.5,46.6]` 与引导环**完全一致**
       - 教训：位置本身在回绕处已经连续（见第 1 条），回绕前后同相位的点本来就几乎重合，**不需要额外补偿**
        - **判断"尾巴对不对"的可靠方法**：把「引导环包围盒」和「尾巴包围盒」分别量出来对比 —— 尾巴是轨迹的一段，两者应当**基本一致**。不一致就说明尾巴被改坏了
    - ⚠ 验收这类"接缝"时，**取样必须按稳定的 `is-cN` 类**，不能按 DOM 下标：三颗星每帧都按 depth 重排，按下标取会把"不同的星"当成同一个、量出**假的 51 单位跳变**（我第一次就是这么误判的）
  - ⚠ **位置要减掉质心**：原值下系统质心在 `z = 0.383254`，投影后会整体偏出 viewBox 中心、各天体轨迹也挤在一起。验证过**总动量本来就是 0**，所以**只需要挪位置、不需要改速度**（这是排查时差点搞错的地方 —— 一开始怀疑动量不守恒，实测发现动量是 0、偏的是质心）
  - **3D 透视**：这套初值本身是**三维**的（z 速度 ±0.629473，z 跨度与 x 同量级）。投影方式是 x 水平、y 按 `TILT_Y = 0.62` 压成竖直分量、z 一部分按 `TILT_Z = -0.46` 参与竖直方向（让"远"的一侧偏上、形成斜向椭圆）、另一部分作为**深度**决定近大远小与前后遮挡（`--z = 1 + depth·0.34`，按系统最大半径归一化）
  - **轨道引导环**：三颗星各画一条**完整轨道**的**虚线**（静止不动，是参考线）。数据直接取自**同一张周期表**（见上），所以环与实跑轨迹永远一致

  - **踩过的坑（都在代码注释里）**：
    1. **CSS `transform` 会完全覆盖 SVG 的 `transform` 属性**。曾把星星位置写进 CSS `transform`，结果属性上的 `translate(...)` 整条失效，星全被摞到原点。现在**定位用外层 `<g transform>` 属性、位移用内层 `.lm-star` 的 CSS transform**
    2. **CSS 自定义属性存数字时是无单位的**：`calc(var(--r) * 0.66 * var(--z))` 这种两个无单位值相乘**不是合法的长度算式**，整条声明会被丢掉（深度缩放一直没生效、`--z` 看着恒定就是这个原因）。改成两个串联的 `scale()`：`scale(calc(var(--r) * 0.66)) scale(var(--z))`
    3. **`transform-box: fill-box` 配 `<rect>` 会把比例算歪**（rect 自带 x/y 偏移），星体被放大到 115 单位而不是 15。改用"以原点为中心的 `<path>` + `scale()` + `transform-box: view-box`"
    4. **柔光不要用实心圆或描边圆环**：实心圆是硬边灰盘、描边圆是粗灰环，都会把星糊住。要用从中心渐隐的径向渐变填充
       - ⚠ 但**"不要光晕"时反过来**：渐变的末端必须是不透明的实色。末端 `stop-opacity=0` 就是那一圈糊边
    5. **离线验证脚本一定要用和组件完全一致的初值**：排查这版时，我的验证脚本把第三个体放在了 `z = 0`（而组件里是 `z = 1.02201`），结果"验证通过"但其实验的是另一条轨道，还因此误判"动量不守恒"。**验证脚本和实现必须共用同一份初值定义**
    6. **"没闭合"要先分清是发散还是整体平移**：一个周期后位置对不上，可能是积分误差（换小步长能救），也可能是质心不在原点（换步长没用、得平移）。这次是后者
    7. **验证周期解至少要跑几十个周期**：只测一个周期的"闭合良好"说明不了任何事 —— 混沌轨道一个周期内可以误差极小、几个周期后就飞出天际。判断"是不是精度问题"的可靠办法是**换一个步长再跑一遍**：若两个步长给出相同的增长率，那就是混沌、不是精度
    8. **不稳定周期轨道要"离线制表 + 按相位播放"**：实时积分会发散，"到点重置"又看得出来在重启；把一个周期预先算成表、之后按相位查表，既永远准确又无缝
       - 接缝要处理**位置**：只在表内相邻两项插值 → 相位回绕时位置跳约 49 单位；跨表尾/表首插值后降到 2.5（正常弧长）

  - ⚠ 量"背景亮度"要取**中部**那条带：页面最底部是纯页面底色，只改壁纸遮罩不会让它变；若要检查底部，得同时确认 `body` 底色也已换掉

- **拓扑页的天幕与全站壁纸像素级一致**：关键是让天幕的**盒子尺寸**、**取景表达式**、**定位基准**三者都与 `.wallpaper-layer` 相同。
  - **`cover` 的缩放比是按「元素自身盒子」算的** —— 这是最容易漏的一点。早期为了盖住筛选条把天幕撑高 44px，`cover` 就把壁纸额外放大约 **5%**（把浏览器分辨率缩到一半时肉眼很明显）。现在天幕用 `position: fixed; inset: 0; height: 100vh`，盒子与壁纸图层**完全相同**（实测 748 vs 748），缩放比精确为 **1.0000**（1500×900 / 1100×700 / 750×450 三种视口均如此）
  - 百分比基准：`fixed` 让 `50%` 以视口为准，与壁纸图层一致（用 `absolute` 时以自身高度为准，会差半格）。祖先用 `overflow-x: clip` 而非 `hidden`——`clip` 不裁剪 fixed 后代，左右方向依然受控
  - 筛选条（`.filter-bar`，y 49..93）**不需要单独处理**：天幕铺满整个视口（0..100vh），它天然就在筛选条之上；筛选条自身透明，于是上下取自**同一层**背景，天然连续
    - ⚠ 曾经有个 `.graph-sky-cap` 想干"盖住筛选条"这件事，但它的 `clip-path: inset(0 0 calc(100% - var(--filter-h)) 0)` 只保留自身顶部 44px，而它 `top: -44px` → 实际可见区是 **y 0..44**，盖的是**顶栏**而不是筛选条。实测把它 `visibility: hidden` 后筛选条像素**完全不变**（`[12,32,59]`），证明它是多余图层；已删除，`--filter-h` 变量也一并去掉。这类"看起来在做某件事、其实没生效"的图层非常误导排查，早删早好
  - 实测：7 个页面在最外侧竖带（版心之外）的像素**完全相同**（取值只有 1 种）
- **通用教训**：CSS 背景的百分比基准是**元素自身**的盒子；`cover`/`contain` 的缩放基准也是**元素自身**的盒子。要让两个尺寸不同的元素显示同一张背景的同一区域，必须让它们的盒子（或视口基准）一致，否则位置和缩放都会差
  1. **`background-color` 画在所有背景图之下**。最初写成 `background-color:#0b1322` + `linear-gradient(rgba(11,19,34,.8) ×2), var(--wallpaper-url)`，那层 80% 渐变把底色整个盖掉，实际呈现的是「壁纸压暗 20%」而非深空色 —— 亮度 29.9，比列表态的深色还亮。于是切换时先变纯色、拓扑挂载后又亮起来，观感就是**背景图闪了一下**。要做纯色就得用**不透明**的面纱；要透壁纸就明确留出透明度。
  2. **`.wiki-view` 的过渡终色必须与天幕最终呈现完全一致**，否则拓扑挂载那一刻会出现亮度台阶。两处统一用 `--graph-veil`（CSS 变量给 `.graph-sky`，JS 侧 `GRAPH_VEIL` 给 `.wiki-view` 的行内样式），实测台阶从 5.7 降到 **1.5**。
  3. **天幕里壁纸的取景必须与 `.wallpaper-layer` 完全一致**（`background-size: cover` + `background-position: center calc(50% + var(--wp-shift))`）。只写 `cover`/`center` 会让同一张壁纸裁到不同位置、亮度对不上，同样产生台阶。
  4. ⚠⚠ **列表 ↔ 拓扑的背景淡入已按用户要求去掉，现在是"直接写入颜色"**（`setPageBg()` 只有一行赋值）。
     历史上这里有过一版 `.bg-fading` 过渡，踩过的坑值得留着（**不要再加回去**）：
     - 它需要"先置 `transparent` → 下一帧写目标色 → 挂 `.bg-fading` 过渡类 → 定时器摘类"这一整套时序，
       因为过渡类**不能常驻**：路由切换的 `<Transition name="page" mode="out-in">` 会读**离场元素自身**的
       transition 属性作为离场时长，根元素上常驻 `background-color` 会把"wiki → 其它页面"的离场
       从 ~180ms 拖到 ~400ms（表现为切到目标页卡一下）
     - 然后又发现两条时间线对不齐：内容淡入 260ms、背景 380ms，内容到位后背景还在变暗，
       观感是"背景单独拖一条尾巴"（用户最初的反馈就是"衔接不自然"）；收到 300ms 才对上
     - 现在没有过渡，上述时序问题**一并消失**：颜色写入即生效
     - 验证方式：逐帧记录 `.wiki-view` 的 `backgroundColor`，确认**首次出现即终值**、
       中间色帧数 = **0**；同时断言根元素的 `transition-duration` 为 `0s`
  5. ⚠ **不要给 `.graph-sky` 单独再加一层 opacity 淡入** —— 它已经跟着父级淡入了
     （天幕的父级是 `.view-body`）。我曾额外写 `opacity: 0` + `.is-in` 类做二次淡入，
     实测**加类与元素挂载落在同一帧**（逐帧记录：元素首次出现时 class 已是 `graph-sky is-in`、
     opacity 已是 1），过渡根本不播，纯属白写一层（已删）。
  6. ⚠ **改任何过渡时，用 CDP 截图是抓不到的** —— `Page.captureScreenshot` 实测间隔约 **750ms**，
     而过渡只有 260~380ms。必须在**页面内用 `requestAnimationFrame` 逐帧记录** computed 值，
     再配合"元素出现/类变化"的时间点判断因果。
     （另有两条路：临时把 `transition-duration` 覆盖成 6s 把过渡停在屏幕上截图；
     或直接改内部状态变量做 A/B。）
  - 验证提醒：测背景稳定性时**不要取包含星系画布的区域采样** —— 画布逐帧绘制自身光晕会带来约 2~3 的自然波动，会掩盖/混淆背景层的真实表现
  - **星系核心 = 一团看不到明显边界的白色光团**（`WikiGraphView.vue` 的 `makeCenter`）。这个需求来回改了四轮，每轮的结论都值得留着：
    1. **「白点太亮」**：原来是纯白内核球 + 纯白径向光晕 + `AdditiveBlending`，叠出一团极亮白斑
    2. **「改用暗红」**：当时把光晕改成**普通混合** + 暗红，理由是"叠加混合下暗红几乎看不见"。结果得到的是**一块不透明的暗红斑** —— 不像光
    3. **「应该是看不到明显边界的光团」**：**关键结论是——实体几何必须删掉**。核心原本是 `SphereGeometry(6)` 的网格，实体表面在屏幕上就是一个**硬边圆**，无论怎么调色都看得出"一个圆盘贴在那里"。光团的边缘只能由**不透明度衰减**造出来，所以核心现在是**纯径向渐变的 Sprite**，没有任何实体几何
       - 于是第 2 轮"必须用普通混合"的结论**被推翻了**：普通混合画不透明色块、会挡住后面的星点；发光本来就该用 `AdditiveBlending`。暗红在叠加下确实偏暗，解法是**多叠几层**而不是改混合模式
    4. **「中心光团还是用白色的吧」（当前）**：颜色改回 `CORE_GLOW_COLOR = 0xffffff`
    - 现在是 **5 层同心 Sprite** 叠加，各层自身都衰减到 0、峰值错开，叠加后沿半径平滑下降，看不出圆边
    - ⚠ **白色比暗红"显亮"得多，所以 opacity 必须压到更低**（当前 0.07~0.18）；五层满不透明度的白会直接叠回第 1 轮那种刺眼白斑（实测第一次改白就冲到亮度 233、接近削顶）
    - ⚠ **光晕贴图的中心不能是"实心亮点"**：色标若在 `0 → 0.1` 保持接近满值，多层叠加后中心会是一个又小又亮的点，肉眼又成了"中心有个点"。现在贴图中心就开始衰减，得到"宽而软的亮心"
    - 实测（以银河原点投影到屏幕的坐标为圆心）：中心 `rgb(188,191,199)`、色度 **11**（白/中性灰）、亮度 **190.6** vs 远场 **60.8**；衰减 `d5=186 → d10=166 → d20=137 → d40=107 → d80=82 → d160=61`，光滑化开
    - 采样技巧三条：① **把世界原点投影到屏幕**再取样，别"找最亮的像素"（旋臂上的白节点比核心亮，找最亮必然找到节点）；② 环上取**分位数**而不是平均（平均会把局部星点/标签糊进来，量出假的台阶）；③ ⚠ **判"有没有硬边"要看每像素变化率，不要看"每 5px 一步降了多少"** —— 光团是中心最亮的高斯型衰减，梯度最大值本来就在中心附近（实测 5px 步降 28.7，即 **5.74/px**），这是"中心亮"的必然结果；真正的硬边圆盘会出现每像素十几到几十的突降
    - ⚠ 原点处**有一个白色节点网格**（投影直径约 7px），所以 `r=0` 那一环的取样会被它主导、量出假台阶；算衰减要从 `r≥10` 起
  - **筛选条要与拓扑图共用同一层背景（否则割裂）**：`.filter-bar` 位于天幕之上且自身透明 —— 只要它底下不是天幕，就会露出"未被深空面纱压过的原始壁纸"，那一条明显比下方星图区亮。现在靠"天幕铺满整个视口"解决：筛选条正落在天幕范围内，上下来自同一层、天然连续。
    - 关键前提：**`.graph-full` 不能 `overflow: hidden`** —— 那会把 fixed 定位的天幕在新版浏览器里照样裁掉（视情况），露出原始壁纸。改用 `overflow-x: clip` 兜住水平方向
    - 验证手法：**逐个隐藏图层再量像素**。藏掉 `.graph-sky` 后筛选条从 `[12,32,59]` 变 `[12,24,42]` → 说明压暗确实来自天幕；藏掉 `.graph-sky-cap` 毫无变化 → 说明那层是多余的
    - 也不要给筛选条加 `backdrop-filter`：那会把壁纸糊掉，而下方星图区是清晰的，质感依然不一致
    - 定位这类层叠/裁剪问题的可靠手法：**把天幕临时涂成纯品红**，再采样筛选条区域 —— 若读到品红即说明天幕确实在它身后
- **拓扑图切换不卡顿**：three.js 场景是同步重活（建几何体/着色器/上传纹理，实测主线程约 130ms）。现在把它推迟到「列表 ↔ 拓扑」的视图过渡（260ms）跑完之后再构建，避免建场景打断过渡动画 —— 实测切换过程最大帧间隔从 135ms 降到 **33ms**（无 >50ms 卡帧）。另外标签页不可见时停掉帧循环，不在后台空烧 GPU；three.js 分包加载期间显示与深空同色的「拓扑图加载中…」等待态，不再留空
- **从 wiki 切到别的页面不再卡一下**：路由切换用的 `<Transition name="page" mode="out-in">` 会读取**离场元素自身**的 `transition` 属性，取其中**最长**的时长作为离场时间。`.wiki-view` 上曾常驻 `transition: background-color var(--dur-ios-3)`（380ms，用于列表↔拓扑的背景淡入淡出），于是每次离开 wiki 都要等约 400ms 才挂载目标页 —— 实测 `wiki → blog` 内容出现 +404ms，而 `tools → blog` 只要 +179ms。
  - 修法：把那条 transition 收进只在切换瞬间挂上的 `.bg-fading` 类，平时根元素没有 `transition`，离场按 150ms 正常结算。实测 `wiki → blog` 从 **404ms 降到 176ms**，与对照的 179ms 齐平（拓扑模式离开同样从约 400ms 降到 210ms），而列表↔拓扑的背景淡入淡出、深空天幕、`colorScheme` 全部保持正常
  - 通用教训：**不要给路由级视图的根元素常驻 `transition`**，它会污染 `<Transition>` 的时长结算
  - ⚠⚠ **还有一条更隐蔽的坑：拓扑页离场时不能带 `transform`**。`.graph-sky` 是 `position: fixed; inset: 0`，而**带 `transform` 的元素会成为 `fixed` 后代的包含块** —— 离场过渡（`.page-leave-active`）会给 `.wiki-view` 加 `translateY(-8px) scale(0.996)`，于是天幕的"视口"变成了"本视图的盒子"：
    - 实测天幕 rect 从 `[0,748]`（铺满视口）跳到 `[49,797]`，**把 y 49~93 那一条让了出来** —— 露出的正是未压暗的原始壁纸
    - 现象就是用户报的"离开拓扑页时背景前几行发亮、一闪而过"
    - 修法：`.wiki-view.page-leave-active / .page-leave-to` 里把过渡限定为纯 `opacity`、`transform: none`。代价是拓扑页离场少了 8px 上移（肉眼几乎看不出），换来天幕在离场全程稳稳铺住视口
    - 回归断言守着：拓扑路由下 `skyRect === [0, 748]` 且 `wikiView.getComputedStyle().transform === 'none'`
  - 定位手法（可复用）：**逐帧记录目标元素的祖先链**，打印每一层的 `transform / filter / contain / will-change` —— 只要某一层不是 `none`，它就成了 `fixed` 的包含块。用 `requestAnimationFrame` 在页面内采样，比 CDP 往返可靠得多
  - 另一条：`syncGraphHeight()` 会在卸载后被 `requestAnimationFrame` 再调一次，用"过渡中"的导航栏位置重算天幕高度。虽然它不是本次闪光的成因，但重算毫无意义，已加 `unmounting` 守卫停掉
- **放大后节点文字保持清晰**：节点标签是 Sprite + CanvasTexture，纹理在创建时按固定字号光栅化；透视相机拉近会把这个纹理放大呈现，越近越糊（实测最近机位下标签屏幕宽约 2473px，而纹理只有 564px）。现在按「参照距离 / 相机距离」推算所需的光栅化倍率（上限 4.8，覆盖到 `controls.minDistance`），拉近时按该倍率重画标签纹理 —— 字号、画布、行高同比放大，而精灵的世界尺寸不变，因此**只提升清晰度、不改变视觉大小**。
  - 重画经过 180ms 去抖；**定时器只排一次**：`scheduleLabelRefresh` 每帧都会被调用，若每帧都 `clearTimeout` 再重设，定时器在持续缩放期间永远等不到触发时机（这是第一版没生效的原因）
- **主题开关**：日/夜滑动开关保持 `div` 结构（内部是一整套 em 基准的绝对定位图层，换成原生 `<button>` 会引入 UA 的 padding/字体/行高/垂直对齐，导致太阳、光晕、云朵、星星整体错位约 3px），无障碍语义用 `role="switch"` + `tabindex` + 键盘事件补齐；**双击开关可恢复「按时间自动」**
- **主题云朵漂移**：从「每秒 querySelectorAll + 逐节点写内联 transform」改为 rAF 合并写入，并在标签页不可见 / `prefers-reduced-motion` 时完全停止

- **路由懒加载**：所有页面按需下载代码块；`three.js`（3D 二维码 / Wiki 拓扑）、`xterm`（控制台）、TipTap 富文本编辑器等重依赖只在实际打开对应页面时加载，首屏不再一次性下载全部页面
- **右侧细进度条**：贴在网页最右缘的一条细线（常态 3px、悬停 6px）表示当前滚动进度；**只在鼠标移到网页右侧 24px 内时淡入**，平时完全不可见。可直接按住拖动跳转。这条同时承担了页面切换 / 懒加载的进度反馈，因此不再另设顶部横条
  - 判定区刻意做窄（24px）：既不打扰右缘附近的页面元素，也不会在正常浏览时被误触发。判定用 `e.clientX >= window.innerWidth - HOT`，**基准是 `window.innerWidth` 而不是 CSS 视口宽**（本站有 `scrollbar-gutter: stable`，两者不相等）
  - 实现要点：进度用 `transform: scaleY()` 表示（不动画 `height`，避免触发布局）；文档高度由 `ResizeObserver` 缓存，鼠标移动只做几何比较，不在 `mousemove` 里读布局（否则鼠标一动就是一次 reflow）
  - 不需要额外的"热区 div"：可见性由全局 `mousemove` 驱动，多一层空元素只会增加 DOM 与认知负担
  - 游戏页（全屏 iframe）按设计不显示
- **响应压缩（br / gzip）**：应用层用 Node 内置 zlib 做 Brotli / gzip 协商压缩，覆盖 API JSON 与静态文本资源（`three.module` 528KB → **123KB**，`editor` 398KB → **约 96KB**）。生产 Nginx 也开了 gzip，但其 `gzip_types` 不含 `text/javascript`，而 Express 对 `.js` 输出的正是该类型，因此应用层这层兜底是必要的
- **分级缓存**：带内容 hash 的构建产物 `max-age=31536000, immutable`；上传图片 / 壁纸 / 桌宠动画 / 游戏资源 `max-age=604800`；`index.html` 为 `no-cache`（发版即时生效）。压缩响应的 ETag 带编码后缀，条件请求正确返回 304
- **插画资源瘦身**：主页卡片图与错误码插画由 PNG 转 WebP（同画质约 **-78%**，合计 4.9MB → 1.1MB）；favicon 由 864×886 / 929KB 换成 32×32 / 3KB；桌宠召唤图标缩到 256×256。可用 `pnpm optimize:assets` 重新生成（需本机装 ImageMagick；产物已提交，服务器无需安装）
- **壁纸层不再重绘**：全站壁纸由 `background-attachment: fixed` 改为固定定位的独立合成层，滚动时只做合成不重绘；当前壁纸显示后会趁浏览器空闲预热「下次要用的那张」
- **桌宠按需加载**：`Mascot`（774 行 + 全部动作表）改为异步组件，不再进首屏 chunk；动画视频 `preload="none"`，首帧动画在浏览器空闲时才开始拉取
- **完整 HTML 文档加载占位**：Wiki 中带外部 CDN / 脚本的完整 HTML 文档在 iframe 加载期间显示“HTML 文档加载中…”占位，不再一片空白
- **分包优化**：Vue 全家桶单独成块，编辑器 / Markdown 渲染独立分包，静态资源缓存更友好
- **后台标签页不空转**：设置页的监控 / 访问统计轮询在标签页不可见时跳过请求，重新可见时立刻补一次；主题云朵漂移动画同样在不可见时暂停

  - 内容区铺一层与主题同色的**长渐变遮罩**：壁纸很花，不压暗卡片文字会被背景吃掉；过渡必须足够长，否则主视觉与内容区之间会出现生硬分界线
- **列表加载骨架屏**（Blog / Wiki 共用 `PostList.vue`）：加载时不再是一行「加载中…」文字，而是**与真实条目同构的占位骨架**（同样的 `.post-item` 外壳与内边距）＋ 逐行错峰的微光扫过。
  - 形状按分类区分：博客是整行条目（2 行摘要 + 右侧箭头），Wiki 是自适应多列卡片（3 行摘要 + 无箭头、更紧凑）—— 尺寸对不上会在内容到达时整页跳动（实测骨架 112px 落在真实卡片 77~124px 区间内）
  - **延迟 150ms 才出现**：命中缓存/本地服务很快时直接出内容，避免"骨架闪一下又消失"的抖动
  - 骨架自身不做入场动画（它是"等待"而非"内容"）。这里有个坑：`.sk-item { animation: none }` 与 `.post-item` 同为**单类选择器、特异性相同**，源序更靠后的 `.post-item` 会胜出 —— 实测骨架条目确实拿到了 `ios-rise-in` 并跟着错峰弹入。必须写成 `.post-items .sk-item` 提高特异性
  - 无障碍上提供 `role="status"` + 视觉隐藏的「加载中…」，`prefers-reduced-motion` 下停掉微光
- **列表逐条入场动画**（`PostList.vue`）：延迟按序号线性递增，并把**总错峰时长**限制在 440ms 内 —— 条目少时接近每条约 80ms 的节奏，条目多时自动收紧到每条约 22ms。
  - 之前是手写 `nth-child(1..4)` 各一个延迟、第 5 条起统一 240ms，于是 Wiki 一页 21 条会"前 4 条依次弹出、剩下 17 条一下全出来"，观感割裂
  - 延迟值由 `staggerDelay(i, total)` 算好后通过 `--stagger` 传给 CSS，不再依赖固定行数；骨架条目不带该变量，因此不受影响
- 顶部显示**公告**：置顶的博客文章会展示在主页（标题 + 摘要，点击进入正文）；未设置置顶时公告自动隐藏。摘要属作者自由填写（可能是装饰符号串），因此限宽 30% 并优先让位给标题
  - **外观**：一枚克制的横条 —— 圆角 **14px**（不是胶囊）、中性细边框、**左侧一道 3px 强调竖条**、`公告` 做成小圆角药丸标签
  - ⚠ 原设计是「999px 胶囊 + 毛玻璃 + accent 描边」，放在居中的 Logo / 一行标语 / 下滑提示之间**像个孤立按钮**，与主视觉不搭（用户反馈"不太搭"）。改法就是去按钮化：收圆角、去强调色描边、层次交给留白与那道竖条
  - hover **不整体上移**（主视觉里位移很跳），改为"底色变实 + 竖条提亮 + 一道高光斜掠扫过 + 箭头右移 3px"，动静更收敛
  - ⚠ **左侧竖条用 `border-left`，不要用绝对定位的 `::before` 矩形**：矩形是直角的，压在 14px 圆角上会在左上/左下露出"方角"、和圆角矩形对不上。`border-left: 3px` 会天然沿圆角走，几何上不可能错位
  - ⚠ **不要加 `backdrop-filter`**：公告条带入场动画，而 `backdrop-filter` 要采样身后内容 —— 元素自身/祖先在做变换动画的头几帧采样不稳定，表现就是"先透明、随后才变成毛玻璃"。底色加实到 92% 即可
  - 窄屏（≤ 某断点）改为两行：第一行 `公告` 标签 + 标题 + 箭头，摘要让到第二行（用 `order` + `flex-basis: 100%`，不用 `justify-content: center` 硬折，否则 `公告` 标签会被单独挤到一行）
- **入场动画一律不要动 `transform`**（`ios-rise-in` 关键帧见 `style.css`、路由入场见 `App.vue`）——
  这是"页面加载好后卡片文字上下小变一下"的根因，`/tools` `/reading` `/anime` `/blog` `/wiki` 都中过。
  这个坑**修了三次**，每次都缩小了量级但没根治，最后才定位干净：
  1. **`from` 帧带 `translateY(18px) scale(0.985)`**：引用它的地方大多是**带延迟**的（`backwards` + `animation-delay`，或按序号错峰），延迟期间元素停在 `from` 帧 —— `opacity: 0` 但**布局已经占位**，于是文字"先以透明状态就位、再自己往上走一段"。实测视口位移 **19px**
  2. **只去掉 `translateY`、保留 `scale`**：位移降到 1~3px，但**变形还在** —— `scale` 以元素中心为原点，缩放会让**元素内部文字整体平移**。仍然看得出"小变一下"
  3. **把 `scale` 的原点挪到顶部**：量级进一步压到 0.4~1.6px，但**它随页面高度增长**
  4. ✅ **最终：入场只用 `opacity`，完全不用 `transform`**
  - 决定性对照（同一份代码、同一帧率采样，量卡片标题的视口 top）：
    · 页面 scale(0.996) 原点居中 → anime **1.09px**、blog 1.0px、wiki 1.2px
    · 原点改 `top center` → anime 1.09px（几乎不变！因为该行在 y≈321，距顶部原点仍有距离）
    · **关掉页面 transform → anime 0.00px**，四个页面全部 0.00px
  - 关键公式：**整页缩放造成的位移 = 距变换原点距离 × (1 − scale)**。所以只要页面上有 `transform`，越靠下的内容位移越大、且**页面越高越明显** —— 无法靠"调小 scale"根治
  - ⚠ **`transform-origin` 要写在 `-active` 类上**，不能只写 `-from`：Vue 只在首帧挂 `-from`，第二帧换成 `-to`，原点若只写在 `-from` 会在动画中途跳回默认值，反而更晃
  - ⚠ **离场保留位移是安全的**：旧页面正在消失，位移不会被读成"内容跳了"，且离场元素不参与布局、不推挤新页面
  - ⚠⚠ **`backdrop-filter` 不能放在"正在入场动画 / opacity < 1"的祖先里**（这条踩了 4 次，已全站清理）。
    浏览器此时无法正确采样背景，**模糊等于没做**，元素只剩那层半透明底色、直接透出页面背景 ——
    浅色主题下页面背景接近纯白，观感就是"刚出现的一瞬间是白色的"。
    - 已修四处：**主页公告条**、**anime 的 `.month-bar`**、**anime 日期选择浮层**、
      **anime 周历的 `.col-head`**（本轮）、**anime 的 `.lang-btn`**（本轮）
    - `.col-head` 的证据链（浅色主题逐帧）：表头自己的背景色**自始至终没变**，
      变的是祖先 `.main` 的 `opacity` ——`ios-rise-in` 带 200ms 延迟且 `backwards`，
      前 200ms 是 `opacity: 0`，随后 `0 → 0.357 → 0.799 → 1`。
      所以只看表头自己的样式**永远查不出来**，必须往祖先链上看
    - ⚠ **去掉模糊后底色必须自己够实**。而且**不能用 `color-mix(..., transparent)` 去调**：
      与 `transparent` 混合时，结果 alpha **不会超过源色的 alpha**；
      `--panel-2` 本身是 `rgb(29 33 44 / 0.66)` 这种带 alpha 的颜色，
      所以把百分比从 70% 调到 92% 都没用 —— 实测浅色主题始终卡在 **0.44~0.5**。
      正确做法：**先用不透明成分（`--overlay-panel`）算出实色，再在最后统一叠一次透明度**
      （现在 `color-mix(in srgb, var(--overlay-panel) 62%, transparent)` → 实测 alpha 恒为 0.62）
    - 回归断言：遍历所有 `backdrop-filter` 元素，检查其候选祖先里有没有
      `animationName !== none` 或 `opacity < 1` 的 —— 有就是风险，7 条路由都必须为 0
  - 排查方法（可复用）：**逐帧记录目标元素与它祖先链的 computed `transform`/`opacity`**。这次就是靠它发现"卡片自己 `transform: none`、动的其实是视图根元素的 `page-enter-*`"——
    只看卡片永远找不到原因；同时要对"关掉 transform"做 A/B 对照才能确认因果，光看漂移数字会被布局自身的 settle（图片加载、骨架替换）干扰

  - **卡片按"放大后头像的视觉中心"对齐，而不是 `.insider-wrap` 的布局中心**：`transform: scale()` 只改变绘制、**布局盒子尺寸不变**，所以放大后的视觉中心比布局中心左移 (28 × 0.55) / 2 ≈ 7.7px。卡片若简单按 `left: 50%` 居中就会整体偏右（实测偏 15px）。修法是 `left: calc(50% - 7.7px)`（变量 `--ic-shift`），实测卡片中心与头像视觉中心偏移为 **0px**
  - 卡片纵向位置取 `top: calc(100% + 13px)`：头像放大后底边下移约 15px，卡片放在"放大后底边上缘 2.6px"处 —— 收起态卡片在头像下方（视觉干净），**展开态与头像相接**，保证「头像 → 卡片」的悬停路径连续（两者是同级子元素，一旦经过空隙就会触发 `pointerleave` 把卡片收起），同时那 2.6px 落在头像下缘空白处、不会盖到脸
  - 卡片用 `visibility` 而非仅 `opacity` 收起 —— 否则收起状态下顶栏的可达性树里仍会带上卡片文字
  - **卡片要浮在顶栏其它部分之上，只给卡片设 `z-index` 是不够的**：`.nav-search` 是 `position: relative`，而 `.nav-end`（卡片的祖先）是 `static` + `z-index: auto`；按 CSS 绘制顺序"定位元素"会盖过"非定位元素的子元素"，实测卡片底部被搜索框压住。修法是把 `.nav-end` 也提为定位元素 + `z-index: 2`
  - **顶栏整体层级必须高于页面里的悬浮控件**：导航栏因 `backdrop-filter` 自建层叠上下文，内部元素再高的 `z-index` 也出不去，能否压住别人完全取决于 `.navbar` 自己的 `z-index`。wiki 页的「列表 / 拓扑图」切换器是 `z-index: 220`，而 `.navbar` 原值 50 —— 会被它压住。现取 **250**：高于页面级浮层（220 及以下），低于所有弹窗层（300+ 详情弹窗、400 虚拟键盘、1000 文件管理），因此不会挡模态。**调整前请确认 221~299 这段区间仍无其它用途**
  - 退出按钮与卡片同色系（半透明面板色 + 常规边框），不用实心色块抢视觉焦点
- **主页彩蛋 `Stella`：让星座连线显形**。主页星空平时**只有星点**、看不出星座；在网页内虚拟键盘输入
  `Stella` 回车后，88 星座的连线**淡入**显形，再输一次收起。
  - 状态放在 `src/composables/uiOverlay.js` 的 `constellationLines`（与 `immersiveView` 同级的轻量 ref 模块），
    **刻意不写 localStorage** —— 这是"看一眼"的临时效果，不该跨会话记住
  - 数据通路：`VirtualKeyboard` 的 `submitCommand()` 里新增 `stella` 分支 → `emit('stella')` →
    `App.vue` 的 `onStellaCommand()` 调 `toggleConstellationLines()` → `ConstellationField` 的 `lines` prop
  - 连线绘制抽在 `lineReveal`（0→1 显形进度）后面，每帧朝目标追赶 `LINE_REVEAL_STEP = 0.045`
    （60fps 下约 0.5s 淡入）；`lineReveal` 太小时（<0.004）整段跳过绘制，省掉无谓的 stroke
  - ⚠⚠ **连线从来就没画出来过 —— `if (j <= i) continue` 把每一对都丢掉了**。
    `items[i].links` 存的是"本折线内的**上一个**点"（`layoutConstellations`：
    `links: prevIdx >= 0 ? [prevIdx] : []`，而 `prevIdx = j > 0 ? items.length - 1 : -1`），
    是**反向**引用：`links[0] = i-1`、`links[1] = i-2` …… 全都 `< i`。
    而绘制循环里写着 `if (j <= i) continue`（原意是"每对只画一次"的去重）——
    于是**没有一条线通过过滤**。这正是用户反馈"敲了 stella 还是没有星座连线"的根因。
    - 这个 bug **在 Stella 功能之前就存在**：星座连线本来一直没被画出来，
      只是没人发现（首页看起来只是"星点很多"）。加彩蛋时才把它暴露出来
    - 修法：直接由"当前点连到它的上一个点"`pos[j] → pos[i]`，天然每个点只连一次、无需去重；
      同时补 `j < 0 || j >= items.length` 的越界保护
    - ⚠ 教训：**"不画"和"画了但看不见"要分开验证**。这个 bug 靠看像素永远查不出来
      （线本来就该是低 alpha 细线）；有效的判据是**数绘制调用**：
      包一层 `CanvasRenderingContext2D.prototype.stroke` 统计每帧描边次数，
      实测"未输入 Stella = 0 笔/帧、输入后 = 256 笔/帧、再输一次 = 0 笔/帧"，
      一眼就能看出是"一次都没画"还是"画了但太淡"
    - 更省事的内部观测手法（本轮用过）：临时在组件里挂一个 `window.__cfProbe` / `window.__cfDraw`，
      直接读 `lines / on / running / lineReveal / drawn` 这类内部量 ——
      比在 DOM 和像素之间反复猜快得多；定位完记得删干净
- **Wiki 单条下载（内部人员及以上）**：Wiki 列表每条右侧有「下载」按钮，导出该条为 zip。
  权限**沿用条目自身的可见性**（`visibilityClause`）：`public` / `insider` 可下，`private` 不下；
  游客没有入口（服务端也会 401）。内部人员本来就能在页面上读到 insider 条目，能读就能下。
  - **为什么打包成 zip 而不是单个文件**：正文常引用 `/uploads` 的图片，只给一个 `.md` 图片就全丢；
    HTML 类条目**本身就是一份自包含文档**（前端用 iframe srcdoc 渲染），把图片一起放进去后，
    解压即可双击打开、与站内所见一致。正文里的链接**不改写**（原文写的是 `/uploads/x.png`，
    与 zip 内的 `uploads/x.png` 同名，相对路径自然命中）—— 既不动用户原文，也不塞 base64 让文件膨胀
  - ⚠ **`visibilityClause()` 对管理员返回 `null`**（表示"全可见"），所以校验里要单独兜住 `private`，
    否则管理员会把 private 条目也下载走，而需求是"内部人员及以上"
  - ⚠⚠ **服务端绝对不能下发 `Content-Disposition`** —— 这是本轮最耗时的坑，务必记住：
    Chrome 看到 `Content-Disposition: attachment` 会把响应当成"下载"处理，
    于是**前端 `fetch()` 拿到的是 204 + 空 body**。实测同一个 URL：
    ```
    带 Content-Disposition  → status=204  blob.size=0
    不带                    → status=200  blob.size=10575
    ```
    现象极具误导性：**服务端日志明明写着"200 / 10575 字节已发送"，浏览器里却是 204**，
    下载下来的 zip 是 0 字节。因为我们是"fetch 取 blob → 自己造 `<a download>` 触发下载"，
    所以必须让服务端只给干净字节、**文件名交给前端的 `download` 属性**。
    顺带还避开另一个坑：该头只能是 ASCII，而 wiki 的 slug 常是中文，直接写会抛
    `ERR_INVALID_CHAR` 把请求打成 500（这个我踩过一次）
  - ⚠ 排查同类"服务端说发了、前端说没有"的问题时，有效手段是**在服务端把"即将发送"的事实写进日志**
    （状态码 + 字节数），再用 CDP 的 `Network.responseReceived` 看浏览器实际收到的状态码，
    两边一对就能确定问题出在链路中间而不是业务逻辑
  - ⚠ `api/posts.js` 的 `authHeaders()` 原来**只读管理员的 `anihub.token`** ——
    内部人员调用时会一个 `Authorization` 都不带，被服务端按游客 401 拒掉
    （实测"内部人员点下载 → 下载失败：请先获取内部人员或管理员身份"）。
    现在改成 `管理员 token || 内部人员 token`；凡是"内部人员也可能调用"的接口都要用它
- **拓扑图页面的加载优化**（`WikiGraphView.vue`）：从导航到画出第一帧，实测 **622~737ms → 364~690ms**
  （稳态约 **370ms**）；`initScene` 的 `markers` 段 21.3ms → **4.7~7.6ms**。
  - **先量再改，别猜**。用 `window.__graphPerf` 把 `initScene` 逐段计时
    （newRenderer / controls / bgStars / center / dust / markers / edges / resize），
    结论是**耗时并不在网络**：three.js 123KB 传输 45~70ms、wiki 列表 API 23ms，全部在 ~200ms 内结束
  - **真正的两处浪费**：
    1. `transitionGuardUntil = now + 340` —— 原意是"等视图过渡（260ms）跑完再建场景、避免打断动画"，
       等于**硬等 340ms**。而结构构建实测只要约 23ms，等满并不划算 → 收紧到 **170ms**
       （只等列表淡出那一段），图提早约 300ms 出现
    2. `makeMarkers` 里 **21.3ms 的大头是"烤 21 张标签纹理"**（每张一个 canvas + CanvasTexture
       + `getMaxAnisotropy()`），但它**不影响第一帧能不能出来** → 拆成两阶段：
       `makeMarkers` 只放"占位精灵"（位置与世界尺寸**现在就能算** —— `sp.scale` 只由文本行数决定、
       与光栅化倍率无关，见 `labelMetricsFor`），首帧先画结构；`makeLabels()` 在**下一帧**再烤纹理
       - 体感从"白等一帧、图和字一起出现"变成"图先出来、字跟着来"
       - ⚠ 拆分的前提是**先确认 `sp.scale` 与倍率无关**（`makeLabelSprite` 里倍率只影响 canvas 分辨率），
         否则占位尺寸与真实尺寸不一致、标签会跳位
  - ⚠ 两阶段后 `refreshLabels()`（缩放时提高清晰度）依赖 `m.label`，仍是有效引用 —— 实测缩放后正常
  - ⚠ 首帧后烤标签的 rAF 回调要用 `unmounted` 标志兜住：卸载后再碰 `renderer` 会崩
  - ⚠ **验证"标签有没有渲染"不要按"纯白像素"找**：标签材质带 tint（`themeTextColor`，约 `#b6bdcb`，
    亮度 ~190）。我第一次用 `L>=235` 判据得到 0 个，误判成"标签没渲染"，而截图里标签全在。
    正确判据是"浅灰字 + 深色描边"：`L>=150` 且 3px 邻域内存在 `L<=40`
  - ⚠ 若以后节点数大幅增长（几十上百条），**结构构建一旦超过约 60ms 就会明显打断淡入**，
    届时应把 `transitionGuardUntil` 调回去；依据就是 `window.__graphPerf` 的合计值
  - ⚠⚠ **白色矩形（刷新时"文字位置先出现白条"）的根因与根治办法**（用户反馈过两轮，第一次没修对）：
    `THREE.Sprite` 的 `SpriteMaterial` **不传 `map` 时用的是默认白色贴图**，而 `Sprite` 永远正对相机 ——
    所以两阶段之间那个"还没烤纹理的占位精灵"，会在这段时间里把每个标签位置画成一块实心白矩形。
    - ❌ **第一版修法（`visible = false`）不够，用户反馈"还是有"**。我当时的验证脚本也"通过"了，
      但那个验证本身有缺陷（见下面"假通过"那条）。改用逐帧推进 rAF 队列的办法复测，
      才拿到真实数据：占位窗口里**浅色像素 23761**，而探针显示 `visible=True` 的精灵里**没有一个缺贴图**
      —— 也就是说"状态全对、画面照旧白"，`visible = false` 在这个路径上**没有真正拦住绘制**
      （three.js 的 `projectObject` 里确实有 `if (x.visible === !1) return`，
      所以**为什么没拦住我没有查清**；不再依赖它）
    - ✅ **根治办法：给占位精灵一张"全黑 1×1 贴图"**（`placeholderTexture()`，全局单例），
      再叠加 `visible = false` 做双保险。这样**即使它被画出来也只是黑色小片**，在深空底上几乎不可见 ——
      不再依赖任何"应该不会被渲染"的假设
    - 实测（同样逐帧推进）：占位窗口浅色像素 **23761 → 89**，`step-5` 截图里白条完全消失
    - 连带三处必须一起改：
      ① `makeLabels()` **不能照抄占位的 `visible`/`opacity`**（照抄标签会永远不显示）；
      ② `refreshLabels()` 同理 —— 若在阶段二之前被缩放触发，也要用新精灵自己的可见性；
      ③ **占位贴图是所有占位共用的单例，`makeLabels()` 里不能 `dispose()` 它**（只能 dispose 独立材质）
  - ⚠⚠ **验证 WebGL 画面时有两个必踩的假通过陷阱**，两个我都踩了：
    1. `readPixels` / `toDataURL` 默认**都拿不到像素**（`preserveDrawingBuffer` 默认 `false`，
       缓冲呈现后即被清）。我第一版脚本所有帧的"非透明像素"都是 0，`Math.max(...)` 落到 0，
       于是"无白块"断言**假通过**。→ 判据必须先自证有效：确认**有效帧数 > 0**，或用 A/B 对照证明判据灵敏
    2. **阈值不能按"接近纯白"取**。白条出现时视图还在淡入（`.view-body` opacity<1），
       白块被混合成**浅灰**（实测 ~200 而不是 250）。我用 `rgb>235 && a>200` 得到 **0 个**，
       又一次误判成"没有白块"，而截图里明明有。
       → 正确判据是"中高亮度 + 低饱和"：`max(r,g,b) >= 190 && max-min <= 18`（并排除顶部标题栏区域）
  - 复现/验收手法（可复用）：**把 `requestAnimationFrame` 换成队列 + 单步释放**，
    这样能精确停在"阶段一完成、阶段二之前"的那一帧逐帧截图，而不是靠猜时机。
    实测 9 步里的关键帧：`step4` 建完结构（浅色 0）→ `step5` 出现白条（正常应 0）→ `step9` 标签到位
  - ⚠ **`watch` 里必须保证有帧在画**，否则改了 `lineReveal` 也看不见。两种循环本来不在跑的情况都要兜住：
    ① `prefers-reduced-motion` —— `start()` 会直接 return，此时改为**直接置位** `lineReveal` 并补一帧
    （不做淡入，符合"减少动效"的本意）；② 不在主页（`on` 为 false）—— 等进入主页时由 `on` 的 watch 统一补帧
  - ⚠ 验收时**不要只用 canvas 像素统计**：连线是 1.45px 低 alpha 的抗锯齿细线，叠在 JPEG 壁纸背景上，
    用"半透明像素数/线条色特征"去数会被星点光晕和星点漂移淹没（实测基线噪声与信号同量级）。
    可靠的判据是**把开启前后的整页截图做逐像素差并放大 6 倍**——线段会呈现为**成条的长直线**，
    而星点闪烁只是零散小点，一眼可辨（差分图见排查记录）
  - `:focus-within` 让键盘 Tab 可达；触屏用 click 切换（`:hover` 在触屏上不可靠）
  - 顶栏任何位置都不出现「匿名模式」「内部人员模式」等文字（只在浮层卡片里），回归断言守着这一点
  - 内部人员能看到游客看不到的页面与文章，但不能编辑、不能进设置页；**进入匿名模式后全站页面都显示壁纸背景**（与 Anime 页共用同一套壁纸与缓存）
- **网页内虚拟键盘的面板必须限宽**（`.vk-panel` 的 `max-width: 680px`）。
  面板原来是 `width: 100%` + `max-width: none`，而按键用 `flex: 1 1 0` / `repeat(10, 1fr)` 平分整行 ——
  面板宽度直接等于视口宽度，于是**在 2K/4K 屏上单个按键会被拉到几百像素宽**，完全不像键盘：

  | 视口 | 修复前 数字/字母键宽 | 修复后 |
  |---|---|---|
  | 3840px | ≈ 376px | **60px** |
  | 2560px | ≈ 248px | **60px** |
  | 1920px | ≈ 184px | **60px** |
  | 1600px | ≈ 152px | **60px** |
  | 768px | ≈ 69px | 60px |
  | 480px | ≈ 40px | 40px（仍满宽，响应式不受影响） |

  - 680px 是折中值：数字键 60px、字母键 60px、最宽的空格键 159px，是正常键盘比例
  - 窄屏（< 680px）时 `width: 100%` 仍然生效，手机端观感不变；`.vk-mask` 是
    `justify-content: center`，面板自动居中
  - 验收方式：用 `Emulation.setDeviceMetricsOverride` 在一个 Chrome 实例里逐个切换视口
    （比反复开浏览器快得多），量 `.vk-key` 的 `getBoundingClientRect().width`，
    确认 ≥768px 时按键尺寸**恒定**、≤480px 时面板仍满宽
- **隐藏登录入口**：界面不显示任何登录按钮，点击顶栏「键盘」按钮打开网页内虚拟键盘，输入 `login` 并回车弹出登录框（Esc 或点击遮罩关闭）；已登录后右上角是一个头像，站点版本号与提交 ID（格式 `版本号.提交ID`）以及 控制台 / 设置 / 退出 都在头像的悬停卡片里

## 快速开始（开发模式，双进程）

```bash
# 1. 安装依赖
pnpm install

# 2. 一键启动前后端（推荐）
pnpm dev:all
# Windows 也可以直接双击 dev.bat；Linux/macOS 可执行 bash dev.sh
```

上面命令会同时启动：

- 后端 API：`http://localhost:3001`（`--watch` 自动重启）
- 前端 Vite：`http://localhost:5173`

按 `Ctrl+C` 会同时停止前后端。

如果不想用一键脚本，也可以手动分两个终端：

```bash
# 终端 A：启动后端 API（端口 3001，--watch 自动重启）
pnpm dev:server

# 终端 B：启动前端开发服务器
pnpm dev
```

打开终端 B 显示的地址（默认 <http://localhost:5173>）。开发模式下 Vite 会把 `/api` 请求代理到后端（见 `vite.config.js`）。

首次启动后端会自动创建 `server/anihub.db`（SQLite）并建表，同时按 `server/.env` 中的配置自动创建站点账号（不存在则新建，已存在则同步为当前密码）。

**站点账号**（个人站，不开放注册）：编辑 `server/.env` 设置 `ADMIN_USERNAME` / `ADMIN_PASSWORD`，改完重启即生效；未设置时默认 `admin` / `anihub-dev-password`（生产环境务必修改）。

## 工作原理

1. 按当前日期计算所在档期（冬 1–3 月 / 春 4–6 月 / 夏 7–9 月 / 秋 10–12 月）
2. 查询 AniList 获取该档期全部动画（`season` + `seasonYear`，按热度排序）
3. 再用这批动画的 ID 查询 `airingSchedules`，得到**每集**的精确放送时间（Unix 时间戳）
4. 结果按档期缓存到服务器 SQLite（媒体列表 7 天 / 排期当前档期 12 小时、过去档期 30 天，分开缓存只重拉过期部分），期间重复加载/切换档期直接读服务器缓存，不重复请求源站
5. 时间戳转本地时区后填入周历 / 月历网格

## 性能与运维说明

以下是本站在加载与运行时做过的主要优化，改动集中在少数几个文件，便于按需回退。

### 传输层（`server/middleware/compress.js`、`server/index.js`）

| 项 | 说明 |
|---|---|
| 压缩 | 应用层用 Node 内置 `zlib` 实现 br / gzip 协商，流式压缩 + 背压透传。**必须放在所有路由之前挂载**，否则包不住 `res.write`/`res.end` |
| 为何不交给 Nginx | Nginx 配置里的 `gzip_types` 不含 `text/javascript`，而 Express 5 对 `.js` 输出的正是该类型 —— 生产环境前端 chunk 实际是未压缩的。应用层这层兜底同时覆盖 dev（Vite 代理）与生产（Nginx 反代） |
| 跳过规则 | 小于 1KB、大于 8MB、图片/视频/字体、`206` 分段响应、已带 `Content-Encoding`、`HEAD` 请求一律放行 |
| 缓存 | `/assets/*-<hash>.js|css` → `max-age=31536000, immutable`；`/uploads`、`/wallpapers`、`/pet`、`/spd` → `max-age=604800`；`index.html` → `no-cache` |
| 条件请求 | 压缩响应的 ETag 会带 `-br` / `-gzip` 后缀（同一 URL 不同编码内容不同），并据此正确返回 304 |

### 数据库（`server/db.js`、`server/routes/visits.js`）

- `PRAGMA synchronous = NORMAL`：WAL 模式下避免「每个页面访问都 fsync 一次」；另有 `busy_timeout`、`wal_autocheckpoint`、`journal_size_limit`、64MB 页缓存
- 访问记录改为**内存缓冲 + 定时批量落库**（满 50 条或 3 秒触发），并设队列上限，异常刷量时不会撑爆内存
- 每 5 分钟 `wal_checkpoint(TRUNCATE)`，每小时清理过期访问记录（默认保留 180 天）；进程退出前也会 checkpoint 并 `db.close()`
- 启动时只在 `.env` 里的密码与库中 hash 不一致时才重算 bcrypt（原先每次启动都无条件算一次）

### 安全（`server/lib/clientIp.js`、`server/middleware/rateLimit.js`、`server/middleware/auth.js`）

- **客户端 IP 取可信来源**：Nginx 用 `$proxy_add_x_forwarded_for`，XFF 的**第一段是请求方可以随便伪造的**。现在统一走 `app.set('trust proxy', 1)` 提供的 `req.ip`，兜底解析也取 XFF 末段。（原先取首段，可被用来绕过限流、伪造访问归属地并触发大量外呼）
- 登录失败限流（15 分钟 8 次封禁）、内部人员口令限流、IP 归属地解析并发上限（2）与队列上限
- `bcrypt.compare` 改为异步；用户不存在时也跑一次等长比对，避免用响应时间探测用户名
- 关闭 `X-Powered-By`

### 前端（`src/`）

- 主题：`resolved` 依赖一个每分钟推进的 tick，**跨 6:00 / 18:00 会自动切换**（原实现用 computed 包 `new Date()`，结果被永久缓存，过点不生效）；手动切换后出现的「自动」小按钮可随时切回
- 壁纸：改为固定定位合成层（不再用 `background-attachment: fixed`），并在当前壁纸显示后空闲预热下一张
- 桌宠：`Mascot` 异步加载 + 视频 `preload="none"` + 空闲时起播；召唤按钮在「有权限但未显示」时一定可点
- 滚动/尺寸监听：滚动指示条不再在每次 `mousemove` 里读 `scrollHeight`（改用 `ResizeObserver` 缓存）；导航栏写 `--nav-h` / `--wp-shift` 前先比较值
- 全局错误兜底：`app.config.errorHandler` 把未捕获异常导向 500 错误码页，不再是白屏

### 插画资源（`scripts/optimize-assets.mjs`）

## 已知说明

- **本地 Web 代理是路径前缀反向代理**（`/local-web/http/<host>:<port>/...`），适合纯静态页面、支持子路径部署的服务和简单 HTTP 服务；如果目标服务硬编码从根路径发起 `/api` 等请求且不支持配置 base URL，可能需要先在服务自身配置子路径前缀，或使用控制台/SSH 做端口转发访问。
  - ⚠⚠ **代理改写过的响应必须绕开压缩中间件**（`server/middleware/compress.js` 已修）。代理在改写 HTML/JS 后用 `res.writeHead(200, headers)` + `res.end(body)` 发送，`writeHead` **立刻提交响应头**；而压缩中间件要做两件必然改头的事（`removeHeader('Content-Length')` 改成 chunked、`setHeader('Content-Encoding')`），对已提交的头调用会抛 `ERR_HTTP_HEADERS_SENT`
    - 这个异常抛在 `res.end()` 的调用栈里 → **uncaughtException**，表现为"响应要么 500、要么连接挂着不断开"
    - 实际症状：**打开 `/local-web/...` 只能看到首页，样式/脚本全部加载不出来**（实测 CSS 返回 500 空体、JS 请求永久挂起）。注意**首页本身是好的**（不会触发压缩路径），所以很容易误判成"代理整个挂了"
    - 修法：`headersAllow()` 里加一条 `if (res.headersSent) return false` —— 头已发出就进入 `raw` 模式原样透传。`Content-Length` 是路由自己算好的，与正文一致，不需要也不应该再压缩
    - 验证：代理首页 + 其引用的全部子资源（实测 1.2MB JS / 362KB CSS）+ 上游 `/api/*` 全部 200，且**站点自身的 gzip 压缩没有被误关**（HTML 仍 `content-encoding: gzip`）
  - ⚠ 排查此类问题要**看服务端 `server.err.log`**，不要只看浏览器控制台 —— 浏览器侧只表现为资源失败/挂起，真正的原因（uncaughtException 调用栈）只在服务端日志里
  - ⚠⚠ **必须把浏览器的 Cookie 转发给上游（只剔掉代理自己那个）**。原先 `hopByHopHeaders()` 里有一条 `delete out.cookie`，把**整个** `Cookie` 都删了。后果：任何"用自家 Cookie 做会话"的本地服务都登不上 —— 上游第一次回 303 并 `Set-Cookie`，代理把它改写成前缀内的 Path、浏览器也带回来了，但转发时又被丢掉 → 上游永远收不到自己的会话 Cookie，一直回 401
    - 症状很好认：**换个本地服务就正常，只有这个打不开**（例如 DSH Web GUI 在 3080）。实测服务端收到的头里 `cookie` 字段**完全缺失**
    - 修法：`upstreamCookieHeader()` 只过滤掉 `anihub_local_web`（代理自己的会话 Cookie，Path 在 `/local-web` 下），其余原样转发
    - 验证手法：起一个"回显所有请求头"的探针服务，让代理转发到它，直接看代理究竟发了什么 —— 比猜快得多
  - ⚠⚠ **必须向上游声明 `Accept-Encoding: identity`**。浏览器会把自己的 `accept-encoding: gzip, deflate` 透传给上游，上游于是回**gzip 压缩体**；而 HTML/JS 的路径改写是**按文本做的**（注入 `<base>`、把 `/api`、`/plugins`、`/assets` 加前缀），拿到压缩字节完全改不动，只能原样透传
    - 后果：目标页面里的绝对路径不带前缀 → 浏览器去**主站**根路径取资源 → 拿到 HTML 而不是 JS → 控制台 `SyntaxError: Unexpected token '<'`，页面空白
    - 实测 DSH 的 `/` 直连就是 `content-encoding: gzip` + `transfer-encoding: chunked`；加上这条后回明文，改写才生效
    - 代价可忽略：本机回环代理，不压缩反而省 CPU
  - ⚠ **改写条件不能要求 `content-length`**。上游常用 `transfer-encoding: chunked`（没有 content-length），老条件 `Number.isFinite(declaredLen) && declaredLen > 0` 直接判否 → HTML/JS 原样透传、`<base>` 不注入
    - 现在：有 length 就按 length 预判，没有就**先收下来**，累积过程中用 `HTML_REWRITE_LIMIT`（10MB）兜住内存 —— 超限立即改写为直通，不再缓存
  - 验收方法（可复用）：造一个**忠实复刻目标服务鉴权行为**的上游（`?token=` → 303 + `Set-Cookie`，其余要求该 Cookie，页面引用绝对路径 `/assets/*`，且只在客户端要 gzip 时才压缩），然后检查：① `?token=` 是否 303 ② `/` 是否明文 ③ `<base>` 是否注入 ④ 资源引用是否都带前缀 ⑤ 子资源是否 200 ⑥ 应用是否真的跑起来
- **中文标题与中文简介为人工维护的映射表**（AniList 不提供中文标题/简介字段）：标题见 [src/data/zhTitles.js](src/data/zhTitles.js)、简介见 [src/data/zhDescriptions.js](src/data/zhDescriptions.js)、类型标签中文翻译见 [src/data/zhGenres.js](src/data/zhGenres.js)，均完整覆盖 2026 夏季档全部正常向作品（成人向除外）；语言为中文时点开详情会优先显示中文简介，未收录的动画回退显示罗马音标题与英文简介。新增条目时在文件中按 `AniList id: '内容'` 追加即可（id 可在动画详情弹窗的 AniList 链接中查到）
